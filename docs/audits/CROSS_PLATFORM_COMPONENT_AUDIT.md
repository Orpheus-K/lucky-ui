# Lucky UI 跨端组件全量审计协议

## 1. 目标与不可妥协项

本审计面向 Lucky UI 可发布组件库，目标是逐组件、逐文件、逐行确认实现质量，并以 H5 与微信小程序真实运行结果闭环。源码推断、单张截图、构建成功、接口返回成功或“看起来正常”都不能单独作为 UI 问题关闭依据。

审计必须同时回答以下问题：

1. 问题能否在组件独立示例中复现，还是只出现在 demo、业务组合或局部覆盖样式中？
2. 根因属于组件实现、主题 token、共享工具、示例用法、文档、测试设施还是平台差异？
3. 问题影响哪些状态、尺寸、主题、视口和平台？
4. 最小且可复用的修复位置在哪里，是否会改变公共 API 或默认行为？
5. 修复前后能否用同一路由、同一选择器、同一数据和同一交互得到可比较证据？
6. 局部修复是否破坏其他组件、组合场景、主题或平台？

## 2. 审计基线与范围

- Git 基线：`develop` 的 `c8071e6`。
- 审计分支：`docs/lucky-ui-full-audit`。
- 审计工作树：独立于已有脏工作树，禁止搬运或覆盖其他工作树中的未提交改动。
- 组件目录：73 个 `lk-*` 组件目录，324 个文件；其中 322 个文本文件共 58,674 个物理行，另有 2 个字体二进制文件。旧矩阵仅统计部分扩展名，不能作为逐行审计分母。
- 共享实现：`components/common`、`core`、`composables`、`utils`、`theme`、`locale`、包入口与发布元数据，共 77 个文件、10,338 个物理行。
- 关联范围：组件导出与类型声明、每个组件的 demo、文档、单元测试、视觉测试、兼容脚本、H5 构建产物、微信小程序构建产物。
- 目标端：H5、微信小程序。其他端只记录静态风险，不作为本轮运行态关闭门槛。

手写代码逐行做语义审查。图标定义、字体映射等生成内容也必须进入文件清单与行数覆盖；对这类文件同时验证生成器、输入、输出数量、重复项、非法值、资源可达性与文件哈希，不能用“生成文件”作为漏审理由。

## 3. 问题分类

每条问题使用稳定编号，例如 `LK-BUTTON-INT-001`，并且只能有一个主分类；相关分类放在标签中。

| 代码 | 主分类 | 必查内容 |
| --- | --- | --- |
| `STY` | 样式 | 选择器、状态样式、主题切换、裁剪、层叠、动画、样式隔离 |
| `ALG` | 对齐 | 基线、图文居中、左右/上下对齐、插槽对齐、长文本对齐 |
| `RED` | 代码冗余 | 重复逻辑、重复样式、重复 token、无效分支、死代码 |
| `SPC` | 边距 | margin、padding、gap、安全区、首尾留白、相邻组件节奏 |
| `NST` | 嵌套 | 无意义包装、过深 DOM/WXML、定位上下文、slot 边界 |
| `ORG` | 散乱 | 职责分散、状态来源不一、魔法值、跨文件耦合、命名不一致 |
| `UI` | UI 合理性 | 信息层级、可读性、反馈强弱、空白、密度、默认形态 |
| `DIM` | 宽高 | 固定尺寸、最小/最大尺寸、溢出、响应式、触控面积 |
| `INT` | 交互 | v-model、事件次数、禁用/只读、焦点、滚动、拖拽、异步竞态 |
| `DOC` | 文档 | Props/Emits/Slots/Methods/CSS 变量、默认值、示例、限制、迁移说明 |
| `CMP` | 兼容性 | UniApp 标签、条件编译、浏览器 API、样式隔离、平台原生能力 |
| `COL` | 颜色 | 语义 token、明暗主题、对比度、禁用态、硬编码色、品牌一致性 |
| `XPF` | 端差异 | H5 与微信的结构、尺寸、样式、事件、滚动、动画和降级差异 |

附加标签可使用 `a11y`、`performance`、`type-safety`、`test-gap`、`demo-only`、`breaking-change`。

## 4. 根因归属规则

按以下顺序判断，禁止先写兜底样式再解释：

1. 在组件独立 demo 使用公开 API 复现：优先归属组件、主题或共享实现。
2. 组件独立 demo 正常，组合后异常：检查 slot、父子上下文、样式隔离、定位与滚动容器。
3. 组件默认行为正确，但 demo 传参、结构或局部样式错误：只修 demo，并补充正确示例。
4. 文档声明与真实 API 不一致：以经过设计确认的公共契约为准，同步实现、类型、测试、demo 和文档。
5. 仅一端异常：先确认编译产物和运行态结构，再判断条件编译、原生控件或样式隔离；不得用另一端正常来否定问题。
6. 三个及以上组件重复出现同类魔法值或补丁：评估主题 token、mixin、composable 或 core 工具层方案。

## 5. 严重度与证据等级

### 严重度

| 级别 | 定义 | 处理 |
| --- | --- | --- |
| `P0` | 无法构建、白屏、数据破坏、核心路径完全不可用 | 立即阻断其他工作 |
| `P1` | 常规用法错误、主要交互失效、跨端明显不一致、公共 API 违约 | 当前批次必须修复 |
| `P2` | 特定状态/尺寸异常、明显视觉或文档缺陷、可维护性高风险 | 排入明确修复批次 |
| `P3` | 轻微一致性、可读性或低风险冗余 | 记录并按收益合并处理 |

### 证据等级

| 等级 | 含义 |
| --- | --- |
| `E0` | 只有猜测或肉眼印象，不能进入正式问题清单 |
| `E1` | 源码、类型、文档或编译产物可确定问题 |
| `E2` | H5 真实 DOM、尺寸、计算样式或交互已复现 |
| `E3` | 微信小程序真实 WXML、offset/size/style 或交互已复现 |
| `E4` | H5 与微信在同一场景完成修复前后对照，并通过对应自动化断言 |

布局、样式、颜色、交互和跨端问题原则上只有达到 `E4` 才能关闭。纯文档、类型或死代码问题可以用 `E1` 加自动化门禁关闭，但必须说明为什么无需运行态证据。

## 6. 每条问题的记录模板

```markdown
### LK-COMPONENT-CATEGORY-NNN 简短标题

- 严重度：P1/P2/P3
- 状态：open/fixing/verifying/closed
- 归属：component/theme/shared/demo/docs/tooling/platform
- 影响：H5 / MP-WEIXIN / both
- 源码基线：commit + 文件哈希
- 复现：route、query、viewport、theme、locale、data fixture、步骤
- 修复前证据：DOM/WXML、selector、rect/offset/size、computed style、事件、console/error
- 根因：定位到文件、符号和具体代码路径
- 最佳方案：为什么选此层修复；拒绝了哪些替代方案及原因
- 修改范围：工作树、分支、文件、公共 API 影响
- 验证：compat、定向 lint/type、unit、H5 build、MP build、H5 probe、MP probe、auto-preview
- 修复后证据：与修复前完全相同的字段
- 回归范围：依赖组件、组合场景、主题、视口
- 结论：closed 或仍未满足的门槛
```

截图只作为辅助附件。正文必须记录结构化数值和可重复步骤。

## 7. 最佳方案选择原则

1. 修复公共默认行为，不在业务页用 `:deep`、硬编码内联值或额外包装掩盖组件缺陷。
2. 保持默认 API 兼容；确需破坏性变更时单独设计迁移方案、版本策略和完整回归。
3. 优先使用现有语义 token；缺少通用语义时新增 token，不能把某个 demo 的视觉值沉入组件默认样式。
4. H5 与微信使用同一语义状态；平台原生能力不同则显式条件编译并记录可接受差异。
5. 移除冗余前先用测试锁定行为，避免把“代码更短”误当成“行为不变”。
6. 异步、计时、监听和手势逻辑必须覆盖取消、卸载、重复触发和边界值。
7. 只为可验证问题修改；不顺手重排无关代码，不把多个独立功能点塞入同一分支。

## 8. 解决步骤

1. 冻结组件源码、共享实现、demo、文档和测试文件清单及哈希。
2. 逐文件逐行阅读，核对 props、emits、slots、methods、样式状态和平台分支。
3. 在确定性演练场中建立最小复现，记录修复前 H5 与微信运行态证据。
4. 判断根因与影响半径，写入问题台账；没有证据的问题保持观察项。
5. 从最新正确 `develop` 为单一功能点创建独立工作树和规范分支。
6. 先补能失败的定向测试或探针，再做最小修复，同步 demo 与文档。
7. 按顺序执行 `compat-check`、定向 lint/type、unit、H5 build、MP build。
8. 对同一路由、选择器、数据和交互重抓 H5 与微信证据；微信验证后执行 `auto-preview`。
9. 检查依赖组件、主题、暗色模式、长文本、空数据、禁用态和常见移动端视口。
10. 仅在全部门槛满足后关闭问题，并更新组件覆盖矩阵。

## 9. 客观验收门槛

### 通用门禁

- `compat-check:strict` 为 0 error；新增 warn 必须有问题编号和运行态结论。
- 定向 ESLint、Stylelint、类型检查、单元测试、H5 构建、微信构建全部成功。
- 组件文档、类型、实现、demo 的 props、默认值、事件与插槽一致。
- H5 和微信运行过程无新增 console error、page error、未处理 Promise 或事件重复触发。
- 320、375、414 CSS px 三个移动端宽度无意外横向溢出；响应式差异必须有设计依据。
- 明暗主题都不出现透明文字、错误继承、不可辨禁用态或硬编码颜色泄漏。

### 结构与尺寸

- 记录根节点和关键子节点的 tag/WXML、class、文本、left/top/width/height。
- 使用 token 或明确契约的尺寸必须精确匹配；跨端比较先统一为 CSS px。
- 非平台原生差异场景，H5 与微信关键尺寸/偏移误差目标不超过 1 CSS px。
- 可点击目标原则上不小于 44×44 CSS px（微信按等效 rpx 验证）；例外必须记录设计原因并验证可用性。
- 长文本、空内容、最大内容、前后插槽都不能导致非预期截断、重叠或跳动。

### 交互

- 一次手势只产生一次公共事件；disabled/readonly/loading 状态不产生被禁止的事件。
- v-model 的输入值、内部状态、发出值和视觉状态一致。
- 浮层验证打开、关闭、遮罩、内容阻止冒泡、滚动锁定、层级、安全区和销毁恢复。
- 手势与滚动组件记录交互前后 scrollTop/scrollLeft、位置、选中值和状态类变化。
- 计时或动画组件使用冻结时间、禁用动画或结构化事件断言，避免用随机截图掩盖波动。

### 颜色与视觉

- 颜色优先来自语义 token；硬编码色必须有资源语义或兼容性理由。
- 普通正文目标对比度不低于 4.5:1，大号文字和非文本关键图形不低于 3:1。
- 确定性场景可以使用截图差异，默认最大差异像素比例 0.5%；动画、Canvas 和字体抗锯齿场景以结构化尺寸/状态断言为主。

## 10. 确定性演练场

演练场复用组件详情页，但增加审计模式，确保 H5 与微信使用相同场景标识和数据夹具：

- 路由参数固定组件、场景、主题、语言、视口档位和随机种子。
- 提供 `base`、`states`、`long-content`、`boundary`、`interaction`、`composition` 六类场景。
- 提供冻结时间、关闭自动播放/动画、固定网络结果和清空持久状态的能力。
- 每个关键节点提供稳定 `data-audit-id`；测试不得依赖易变层级或展示文案定位。
- 页面输出当前 commit、场景配置和组件版本，证据可以反查源码基线。
- H5 用 Playwright 读取 DOM、矩形、计算样式、滚动和错误。
- 微信用开发者工具 CLI 与 `miniprogram-automator` 读取 WXML、offset/size/style、组件数据和错误。
- 原始截图、日志和 JSON 放在 `artifacts/<feature>-runtime/`，默认不提交；问题文档保留必要结构化摘要。

演练场属于独立功能点，必须在单独工作树与 `feature/component-audit-playground` 分支实现，不能混入审计文档或具体组件修复。

## 11. 工作树、分支与交付规则

- 审计文档：`docs/lucky-ui-full-audit`。
- 单组件缺陷：`fix/<component>-<issue>`，一个功能点一个工作树。
- 共享主题或工具缺陷：`fix/theme-<issue>`、`fix/core-<issue>`，只包含同一根因影响的组件。
- 仅文档缺陷：`docs/<component>-<issue>`。
- 演练场：`feature/component-audit-playground`。
- 每个分支只暂存任务相关文件；提交、PR、描述和文件中不得加入 AI、机器人或辅助生成署名。
- 普通修复目标分支为 `develop`，不得直接推送 `main` 或 `develop`。

## 12. 全量确认与防掩盖规则

所有问题关闭后再执行一次独立总回归，不能复用“修复时刚好通过”的结论：

1. 从干净 `develop` 集成候选创建新的验证工作树。
2. 重新生成组件与文件哈希，确认 73 个组件和共享实现无漏项。
3. 重新执行静态兼容、代码规范、类型、全量单测、H5/微信构建。
4. 按风险分层重跑全部确定性场景；高风险组件全场景，中低风险至少覆盖基础、边界、交互和组合场景。
5. 重新抓取 H5 与微信运行态，不沿用修复分支的缓存或旧证据。
6. 检查全局主题、浮层层级、滚动锁定、表单联动、长列表、图表和安全区等跨组件链路。
7. 对未关闭项、可接受差异、跳过项逐条给出证据与责任，不允许用总体通过率隐藏单项失败。

## 13. 当前基线事实

- `compat-check --strict`：0 error、60 warn；但微信构建仍报告 `select` 与 `img` 选择器不受支持，证明当前扫描器存在确定性盲区，不能单独作为兼容通过结论。
- 兼容风险矩阵：4 个高风险、31 个中风险、37 个低风险。72 行中包含并非独立组件目录的聚合项 `lk-chart-lite`，实际只覆盖 71/73 个组件；`lk-root` 与 `lk-preload-debugger` 漏项，修复前不能把矩阵当作全覆盖证明。
- 缺少组件单测：`lk-form-group`、`lk-page`、`lk-root`、`lk-tab`。
- `lk-preload-debugger` 没有同名独立 demo 文件，但当前已嵌入 preload 演练页；必须以场景 registry 和真实路由判断可达性，不能只按文件名判定“没有演练场”。
- 73 个组件都有主组件、props 文件、`defineOptions`、`baseProps`、`customClass` 和 `customStyle`。
- 初步模式扫描发现硬编码颜色、浏览器 API、`!important`、硬编码 z-index 等观察项；这些只是定位线索，必须逐项排除资源数据、条件编译和合理特例后才能登记为缺陷。
- 完整基线命令、H5 Peekit 抓取和微信自动化阻塞证据见 [基线结果](./BASELINE_RESULTS.md)。

所有组件的逐项状态见 [组件审计矩阵](./COMPONENT_AUDIT_MATRIX.md)。
